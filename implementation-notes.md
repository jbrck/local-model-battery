## Design Decisions

**[standard.toml, legs.toml, variables.toml — 2026-11-12]**
Category: Design Decision
Spec: the plan called for `standard.toml` (frozen caps/limits/seeds/ctx/budgets),
`legs.toml` (leg catalog) and `variables.toml` (knobs plus measured effects).
Implemented: three flat TOML files at the repo root, loaded with stdlib `tomllib`.
Item counts and budget floors live in `standard.toml` only; `legs.toml` does not restate
them, and the loader joins them by leg id. A comparability key on a leg must map to a
`stamp_key` on some variable, or the catalog check fails.
Reason: one frozen number per leg. Restating counts in two files invites the drift that
already happened between the 3080 and 3090 result sets.

**[scripts/lib/config.py — 2026-11-12]**
Category: Design Decision
Spec: not specified.
Implemented: six small helpers (load, merge, dotted read, path resolve, field check,
hash prefix). Python floor raised to 3.11 so `tomllib` is available rather than shipping a
hand-rolled TOML parser.
Reason: the repo already claimed 3.10+; a parser is a liability and 3.11 is two years old.

**[variables.toml classes — 2026-11-12]**
Category: Design Decision
Spec: "identify variables that would influence those decisions... what capping tokens,
context length, setting thinking on or off would do to the test."
Implemented: three classes. `M` measurement (moves the number, must match across a table,
deviation gets stamped), `C` capacity (moves speed and runnability, logged per host),
`D` dependency (missing means the leg is skipped with a reason). 26 entries, each carrying
the measured evidence and its source.
Reason: a battery that cannot say which of its own knobs is load-bearing will publish
incomparable rows. The class is what a tool is allowed to do with the knob.

**[scripts/lib/legs.py, scripts/lib/variables.py — 2026-11-12]**
Category: Design Decision
Spec: the plan wanted `--validate` CLIs inside the loaders.
Implemented: loaders stay importable and CLI-free; `scripts/check_catalogs.py` is the single
validation entry point.
Reason: AGENTS.md one-responsibility-per-file, and it keeps the path bootstrap out of lib
modules that other code imports.

## Deviations

**[standard.toml `[data]` — 2026-11-12]**
> Spec said: `limits.lcb_data_sha16` holds the LCB dataset pin.
> Implemented: the pin lives in `[data].external` as `lcb_data.sha256_16`, alongside the
> bundled dataset hashes.
> Reason: one place for data identity. The original put it under `limits`, which is where the
> item counts live, so a reader had two places to check for "same data".

**[leg identity — 2026-11-12]**
> Spec said: the reference box runs 13 legs; the plan modeled `math_he` as one leg.
> Implemented: MATH-500 and HumanEval+ are two legs, matching this repo (which already ships
> separate scripts) and the result tables (which have separate columns). Still 13 mechanical
> legs once `selftest` is counted as a gate rather than a scored leg.
> Reason: the two benchmarks score differently (sympy equivalence vs. executed test suites)
> and belong in different columns.

**[hermesagent20 comparability keys — 2026-11-12]**
> Spec said: keys `case_timeout, sandbox_image, agent_commit`.
> Implemented: `agent_commit` became `harness_version` (the same pin), and a new
> `case_timeout` variable was added so the key resolves.
> Reason: the catalog check proved the key had no variable behind it. `case_timeout` is the
> single most expensive hidden cap we have measured, so it earns its own entry.

## Tradeoffs

- **Full SHA-256 vs. prefix.** The bundled datasets carry `sha256_16` (first 16 hex digits)
  rather than a full digest. The catalogue was written from a computed-prefix listing, so
  full digests would have to be regenerated by hand for each file. 64 bits is ample for
  detecting a swapped dataset; it is not a security control.

- **Adapters vs. native ports.** The plan defaults to wrapping the three third-party
  harnesses with a version pin and a prerequisite check. Reimplementing LCB's executor or the
  HermesAgent-20 sandbox would be a multi-week project and would produce numbers that are no
  longer comparable with the published ones.

- **Validation strictness.** The catalog check refuses a leg whose extra comparability key
  has no variable behind it. That is stricter than the plan asked for and it already caught
  five real gaps, but it means adding a leg can fail the build until a variable entry exists.

## Open Questions

**[Whole rebuild — 2026-11-12]**
Category: Open Question
The four scope forks from the plan are still unanswered. Work so far is deliberately limited
to the parts that are identical under every answer.
1. Leg scope: all 13 plus the writing suite, or a subset?
2. Third-party harnesses: wrap with a prereq check (current default), or reimplement?
3. Repo structure: does this public repo become the single source with the reference box's
   harness folded in as profiles and serve lines, or does the box keep a private harness?
4. Writing scoring: this repo's CHANGELOG 2.0.0 replaced pairwise prose ELO with the 138-task
   rubric suite, citing a 75% first-slot bias. Herman's standing note still says pairwise ELO
   only, never absolute scores. Which is current? Nothing was deleted either way; the
   pairwise code is already gone from the repo.

**[Legs 6-13 — 2026-11-12]**
Category: Open Question
Nine legs are cataloged but their scripts are `port_pending`: they exist on the reference box
as `/mnt/data/agents/hermes/workspace/{bench_full,bench_gpqa,bench_mmlu,bench_ifbench,bench_lcb,refusal_bench,reasoning_bench,instr_follow2}.py`
and have not been ported here. Every one of them hardcodes `/mnt/data/benchmark-results` as
its default output directory and several hardcode `/mnt/data` data paths, which is the main
portability blocker. Porting them is the next chunk of work and depends on answer 1.

**[Reference box — 2026-11-12]**
Category: Open Question
Nothing on the reference box was touched. Its harness at `/mnt/models/bench/arete-harness`
still runs the v1 standard. Migration is gated on answer 3 and on a dry run comparing output
