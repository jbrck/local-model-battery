## Design Decisions

**[standard.toml, legs.toml, variables.toml — 2026-11-12]**
Category: Design Decision
Spec: the plan called for `standard.toml` (frozen caps/limits/seeds/ctx/budgets),
`legs.toml` (leg catalog) and `variables.toml` (knobs plus measured effects).
Implemented: three flat TOML files at the repo root, loaded with stdlib `tomllib`.
Item counts and budget floors live in `standard.toml` only; `legs.toml` does not restate
them, and the loader joins them by leg id. A comparability key on a leg must map to a
`stamp_key` on some variable, or the catalog check fails.
Reason: one frozen number per leg. Restating counts in two files invites the drift that
already happened between the 3080 and 3090 result sets.

**[scripts/lib/config.py — 2026-11-12]**
Category: Design Decision
Spec: not specified.
Implemented: six small helpers (load, merge, dotted read, path resolve, field check,
hash prefix). Python floor raised to 3.11 so `tomllib` is available rather than shipping a
hand-rolled TOML parser.
Reason: the repo already claimed 3.10+; a parser is a liability and 3.11 is two years old.

**[variables.toml classes — 2026-11-12]**
Category: Design Decision
Spec: "identify variables that would influence those decisions... what capping tokens,
context length, setting thinking on or off would do to the test."
Implemented: three classes. `M` measurement (moves the number, must match across a table,
deviation gets stamped), `C` capacity (moves speed and runnability, logged per host),
`D` dependency (missing means the leg is skipped with a reason). 26 entries, each carrying
the measured evidence and its source.
Reason: a battery that cannot say which of its own knobs is load-bearing will publish
incomparable rows. The class is what a tool is allowed to do with the knob.

**[scripts/lib/legs.py, scripts/lib/variables.py — 2026-11-12]**
Category: Design Decision
Spec: the plan wanted `--validate` CLIs inside the loaders.
Implemented: loaders stay importable and CLI-free; `scripts/check_catalogs.py` is the single
validation entry point.
Reason: AGENTS.md one-responsibility-per-file, and it keeps the path bootstrap out of lib
modules that other code imports.

## Deviations

**[standard.toml `[data]` — 2026-11-12]**
> Spec said: `limits.lcb_data_sha16` holds the LCB dataset pin.
> Implemented: the pin lives in `[data].external` as `lcb_data.sha256_16`, alongside the
> bundled dataset hashes.
> Reason: one place for data identity. The original put it under `limits`, which is where the
> item counts live, so a reader had two places to check for "same data".

**[leg identity — 2026-11-12]**
> Spec said: the reference box runs 13 legs; the plan modeled `math_he` as one leg.
> Implemented: MATH-500 and HumanEval+ are two legs, matching this repo (which already ships
> separate scripts) and the result tables (which have separate columns). Still 13 mechanical
> legs once `selftest` is counted as a gate rather than a scored leg.
> Reason: the two benchmarks score differently (sympy equivalence vs. executed test suites)
> and belong in different columns.

**[hermesagent20 comparability keys — 2026-11-12]**
> Spec said: keys `case_timeout, sandbox_image, agent_commit`.
> Implemented: `agent_commit` became `harness_version` (the same pin), and a new
> `case_timeout` variable was added so the key resolves.
> Reason: the catalog check proved the key had no variable behind it. `case_timeout` is the
> single most expensive hidden cap we have measured, so it earns its own entry.

## Tradeoffs

- **Full SHA-256 vs. prefix.** The bundled datasets carry `sha256_16` (first 16 hex digits)
  rather than a full digest. The catalogue was written from a computed-prefix listing, so
  full digests would have to be regenerated by hand for each file. 64 bits is ample for
  detecting a swapped dataset; it is not a security control.

- **Adapters vs. native ports.** The plan defaults to wrapping the three third-party
  harnesses with a version pin and a prerequisite check. Reimplementing LCB's executor or the
  HermesAgent-20 sandbox would be a multi-week project and would produce numbers that are no
  longer comparable with the published ones.

- **Validation strictness.** The catalog check refuses a leg whose extra comparability key
  has no variable behind it. That is stricter than the plan asked for and it already caught
  five real gaps, but it means adding a leg can fail the build until a variable entry exists.

## Integration state (2026-11-12)

- Every one of the 14 leg entries in `legs.toml` now points at a real in-repo script;
  `check_catalogs.py` reports 14 in repo, 0 pending.
- `standard.toml` pins nine bundled item files (four added this pass: ifbench 300, mmlu 500,
  reasoning 8, refusal 70), and a test enforces that the bundled set equals the set of item
  files the legs declare.
- The harness default endpoint is env-overridable (`BATTERY_DEFAULT_ENDPOINT`). The test
  package points it at a dead port, so a leg test that forgets `--endpoint` fails instantly
  instead of quietly calling whatever is listening on the operator's machine. One leg test
  had been passing that way against a live server.
- Host env overrides take the plan from 8 runnable legs to 12: `LCB_DATA`, `LCB_SRC`,
  `NLTK_DATA`, and the benchmark venv on `PATH`. `writing` stays skipped until a judge model
  is configured, which is the intended behaviour.
- Known gap: the `nltk_data` prereq check probes the interpreter running the planner, not the
  IFBench verifier interpreter (`--ifbench-python`). With `NLTK_DATA` set and the benchmark
  venv on `PATH`, ifbench still reports "the nltk module is not installed". Fix is to run the
  nltk probe through the verifier interpreter and have the planner pass `--ifbench-python`.
- Quality gate: the full gauntlet run fails on 63 methods (2 complexity, 49 coverage, 36
  CRAP). Failures span legacy scripts (`report_scores.py`, `validate_suite.py`,
  `score_writing.py`, `build_scoring_corpus.py`) and the new leg scripts, whose error
  branches are thin. Not addressed in this pass; `--changed` is the per-commit mode.

## Open questions carry their measured cost (2026-11-12)

- Every decision that needs the operator now prints the measured effect from `variables.toml`
  next to it, so the sheet says what choosing differently costs rather than only which knobs
  exist. Rows the standard owns stay quiet; repeating the catalog at all 47 of them would bury
  the two or three that matter.
- `thinking` becomes an operator question when the weights do not fit the card: on is the
  standard, off is a different measurement, and the row carries both the measured cost of the
  switch and the reason (spilled weights pay RAM bandwidth for every reasoning token).
- A window limited below lcb's budget now names lcb and says what it breaks: below 114688 plus
  headroom that leg stops at the context limit instead of scoring what its cap allows.

## The v1 scoring toolchain is gone, and the judge is pinned (2026-11-12)

- Deleting beats testing what nothing calls: `report_scores.py`, `validate_suite.py`,
  `score_writing.py`, `build_scoring_corpus.py`, `lib/reporting.py` and the v1 writing
  test are removed. The v2 writing leg generates with `bench_writing_generate.py` and
  scores through `lib/judge.py`, so the three-phase path was dead weight still carrying
  a gate bill. That single deletion cleared 31 of the 51 gate failures.
- `lib/reporting.py`'s only live callers were `elapsed` and `start_timer` in the
  orchestrator. Two functions now live where they are used.
- The standard pins the judge model (`standard.toml [judge] model = "nous-glm-5-3-flash"`).
  The judge is a comparability key, so it cannot be a per-run guess; the endpoint stays the
  operator's, and empty means the endpoint the run itself uses. `--judge-model` still wins.
- The plan sheet now names the layer that set the judge: `(standard)` when the pin supplied
  it, `(profile)` when the operator did. Before this the sheet credited every judge to the
  profile, including a judge no profile ever mentioned.

## The leg that needed another interpreter (2026-11-12)

The LCB leg could not run under the orchestrator at all. `lcb.load_helpers` imports
`lcb_runner` from the checkout named by `--src`, and that package needs `datasets`, which the
repo's own venv does not carry. `leg_command` launched every leg with `sys.executable`, so the
leg raised `ModuleNotFoundError` before the first request. The legacy runs never saw this: they
prepended `/mnt/data/benchmark-venv/bin` to `PATH`. A `# pragma: no cover` sat on exactly that
import, so the gate had no opinion about it.

A leg entry can now declare `interpreter`. `run_battery.leg_command` runs the leg under it and
falls back to `sys.executable`. `legs.validate_legs` rejects a relative interpreter, because the
orchestrator runs legs from its own working directory. The plan sheet carries an
`interpreter:<leg>` dependency row, so the operator meets the choice with the rest of the setup.
When the interpreter is wrong anyway, the leg writes status `not run` with the failing
interpreter named in `reason` and `wrong_interpreter`, rather than a traceback that reads like a
model failure: nothing about that run is the model's fault.

The test is a fake checkout (five small modules) rather than a skip, so the import, the prompt
call, the extraction fallback and the cwd restore all run in CI. `load_helpers` keeps its
inline imports, since the checkout path is a runtime flag; it now raises `CheckoutImportError`
instead of letting a bare `ImportError` escape.

Lesson: a leg that shells out to another venv's tool is fine, but a leg that *imports* from
another venv has to run under that venv. Say which interpreter on the leg entry, or the run
dies at minute zero with a message that blames the wrong component.

## The judge is a second model, and it has its own failure modes

The writing leg scores with `nous-glm-5-3-flash` through LiteLLM. As first wired it scored
nothing, and every sign of that was quiet.

`run_battery.py` forwards `--judge-model` and `--judge-endpoint` to the leg but never the key, and
the leg defaulted `--judge-api-key` to `not-needed`. Behind a gateway that requires one, every
judgement is a 401. Generation is a separate step, so the leg still wrote 84 answers and still
passed.

With the key in place the next failure was the model's dialect. GLM-5.3-flash is a thinking model:
it spent the full 1200-token `JUDGE_MAX_TOKENS` budget in `reasoning_content` and returned an empty
`content` with `finish_reason=length`, four calls out of four. `score_answer` called
`chat_request(..., allow_reasoning_fallback=True)`, which handed the reasoning monologue to the JSON
parser. Nothing parsed. `judge_scored=0, judge_errors=705`, and because the block's status came from
generation the leg reported `pass` with `mean_score: 0.0` - a passing zero, which is the worst way
to present a broken measurement.

Three changes:

- `judge.score_answer` posts through `post_chat` with `extra_body={"reasoning_effort": "none"}` and
  reads `answer(allow_reasoning_fallback=False)`. A judge that only thinks is a judge that did not
  score, and the fallback that hid it is gone. Measured after: 2.5-4.6 s per call, valid JSON, mean
  2.83 on a deliberately bad answer (Hook 1, under the anchor) and 8.67 / 8.00 on a good one.
- The key resolves `--judge-api-key`, then `WRITING_JUDGE_API_KEY`, then the run's `--api-key`, then
  `not-needed`. The judge normally shares the run's gateway, so the run's key is the right default.
- `unscored_judge` rewrites the block when `judge_scored` is 0: status `not scored`, the judge named,
  the error count, and the first error quoted. `scoring_extra` carries `judge_first_error` to make
  that possible.

The diagnosis path matters as much as the fix. `_why_no_score` names the three cases in the order
they happen - transport failure, reasoning-only reply, unparseable prose - so the next operator reads
why the judge produced nothing instead of re-deriving it. Same shape as `wrong_interpreter` on the LCB
leg: when a leg fails for a reason that is not the model, the block has to say so.

`setup.sh` also ran `unittest discover -s tests` without `-t .`. `tests/__init__.py` points
`BATTERY_DEFAULT_ENDPOINT` at a dead port so the endpoint guard has something to refuse, and that
import only runs when the tests load as a package. Without `-t .` a fresh clone reported three
failures before the operator ran anything. A setup script that ends in a red suite is worse than no
setup script.

## The interpreter path pointed at a python that could not run the leg (2026-11-12)

The entry above put an absolute path on the LCB leg: `/mnt/data/benchmark-venv/bin/python3`. Two
things were wrong with it. Only the second one showed up in a test.

That path is a symlink to `/usr/bin/python3`, and that interpreter cannot import `datasets` either.
So the fix in the entry above moved the failure instead of removing it. The catalog's one
machine-local path named an interpreter that would have failed this leg at minute zero, on the
machine the path was written for.

The capability check asked for the wrong module. It wanted `lcb_runner`, which no interpreter can
supply: `adapters/lcb.py` puts the checkout on `sys.path` at run time (`--src`, defaulting to
`LCB_SRC`), so that name only resolves inside the leg. The interpreter has to supply `datasets`.

The leg now names a variable and a capability, never a path:

```toml
interpreter_env = "LCB_PYTHON"
interpreter_imports = ["datasets"]
```

`resolve_interpreter` resolves in order: `LCB_PYTHON` in the environment, then
`interpreters.LCB_PYTHON` in `standard.toml`, then a legacy absolute `interpreter`, then
`sys.executable`, stamping which one won. The plan emits the `interpreter:<leg>` row only when the
resolved path is not the orchestrator's own, and the row names the resolution source. The capability
check imports `interpreter_imports` under the resolved interpreter and marks the leg `not run` when
they are absent, so a path that cannot carry the leg fails at plan time instead of hours in.

The catalog names the variable. The host names the path. A standard carrying
`interpreters.LCB_PYTHON` keeps the catalog portable and still lets one machine override it from the
environment.

Lesson: a capability check is only worth having when it checks what the interpreter actually
supplies. Checking a name the leg puts on `sys.path` itself proves nothing and passes nowhere.

## The spec the battery is held to (2026-11-12)

Four requirements, and where each stands:

1. **Read the hardware, the model and the engines available.** Hardware and model are done
   (`env_probe`, `model_probe`). Engines are not: nothing enumerates llama.cpp, vLLM, EXL3, Ollama
   or Strata, and nothing maps a model to the engines that can serve it. Plan tasks 5, 6, 8.
2. **Guide the operator through the variables that would change the score.** Done. The decision
   rows carry chosen against alternative, the consequence and the source of each number, and
   `variables.toml` records what each variable measured.
3. **Run detached and save results along the way.** Neither exists. Plan tasks 11 and 12.
4. **Output the report.** Missing, and the absence is self-inflicted: `3ffe4ce` deleted the v1
   reporting toolchain (`report_scores.py`, `build_scoring_corpus.py`) and put nothing in its place.
   Plan task 13.

### Deviations

**[Task 11 — 2026-11-12]**
Spec said: `--status` reads `run.json`.
Implemented: there is no `run.json`. The run directory holds `MANIFEST.json`, `run-plan.json`,
`legs/*.result.json`, `logs/*.log` and `NOTES.md`. `--status` reads those.
Reason: the plan named a file the orchestrator never wrote. A status command reading it would have
reported every run as empty.

**[Task 13 — 2026-11-12]**
Spec said: the report reads `run.json` and the leg result files.
Implemented: the same correction. The report reads `MANIFEST.json`, `run-plan.json` and
`legs/*.result.json`.
Reason: as above.

**[Task 11 — 2026-11-12]**
Spec said: re-execute under `setsid`.
Implemented: `subprocess.Popen(..., start_new_session=True)`.
Reason: that is the same syscall without depending on the `setsid` binary being installed or on
shell quoting. The child's session is set before it can be signalled.

### Design decisions

**[Task 11 — 2026-11-12]**
Category: Design Decision
Spec: not specified
Implemented: the pid file records the pid and the run directory together, and a pid whose process is
alive but is not this run is called out as such.
Reason: a bare pid file cannot tell a running battery from a recycled pid, and the second one reads
as a hang. Liveness is checked with `os.kill(pid, 0)` and nothing is ever signalled.
